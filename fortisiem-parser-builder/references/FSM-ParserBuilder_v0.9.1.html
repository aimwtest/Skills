ParserBuilder User Guide

How the workspace, tools, and validations fit together

1. Demo View (Load / Refresh)

ParserBuilder opens with a working example already loaded — a Kemp LoadMaster parser in the Parser XML editor and a matching set of entries in Raw Log Samples — so you can see real matches, attributes, and diagnostics before writing anything yourself.

  • Load: this demo is what you see the first time the page opens.
  • Refresh: reload the browser page (⌘R / F5) at any time to bring the demo back exactly as shipped — handy after experimenting if you want a known-good reference again.

The demo is only a starting reference. It's replaced the moment you start editing — or immediately if you click New (see next section).

2. Starting a New Parser Design

  • Click New in the top bar to clear both the Parser XML editor and the Raw Log Samples pane and start from a blank workspace.
  • Open the Create Base Parser tool (Tools sidebar → Main) to scaffold the minimum structure every parser needs — pattern definitions, an event format recognizer, and a parsing instructions block — as a starting skeleton you fill in.
  • Use Format XML at any time to re-indent and tidy the editor's contents.
  • Use Validate to run the diagnostics pass on demand (see Section 6) and Download XML once you're ready to save the parser file.

3. Using the Parser XML Editor

The center editor is where the parser's XML lives — patternDefinitions, eventFormatRecognizer, and parsingInstructions — and it's fully hand-editable.

  • Line numbers track each real line of XML and stay aligned even when a long line wraps onto multiple visual rows — wrapped continuation rows don't get their own number.
  • Auto-complete suggests XML tags, attribute names, <:patternName> pattern references, and $variable names as you type, sourced from what's already defined earlier in the document.
  • Tool output is inserted directly into the editor at your cursor (or appended) instead of being copied to the clipboard — build a fragment with a tool, click Insert into Parser XML, and keep going.

4. Using Raw Log Samples & Matched Pattern Preview

  • Click ✏️ Edit Samples to switch the panel into edit mode — one raw log line per sample. Click ✓ Done to return to the preview.
  • The preview shows, per sample, exactly what the current Parser XML matched — field by field — so you can see extraction results update live as you edit the XML.
  • Placing the cursor inside a single instruction narrows the preview to just that instruction's result; placing it outside any instruction (e.g. at </choose> or the document root) switches to cumulative view, showing everything matched so far for that log.
  • Click a matched row in the preview to jump the editor to its source — the whole enclosing instruction is highlighted (not just the one matched field), so you can also see anything that didn't match.

5. Using the Tools

The left sidebar groups every parserFunctionator builder under Main and Advanced. Open a tool, fill in its form, and use its Insert into Parser XML button to append the generated fragment straight into the editor.

Main

Create Base Parser — scaffolds a blank pattern/recognizer/instructions skeleton to start a new parser.
Regex Parser — builds a collectAndSetAttrByRegex block from a sample line.
Pattern Definitions — defines reusable named regex patterns for reference elsewhere via <:name>.
Pattern Builder — assembles a regex from built-in FortiSIEM pattern tokens (gPat*) without memorizing syntax.
Key Value Pair — generates extraction logic for key=value style log bodies.
JSON Parser — generates attribute-extraction instructions for JSON-formatted logs.
JSON Prettyfier — reformats a raw JSON sample for easier reading before building rules.
By Position Parser — extracts fields by fixed character offset instead of regex.
XML Tag Parser Builder — generates extraction rules for XML-tagged log bodies.
SNMP Trap Function — builds parsing logic for SNMP trap OIDs/varbinds.
Choose/When Logic — quick reference for building <choose>/<when> branches.
When Tests — reference for the test operators/functions usable inside a <when test="…">.
Choose/When Creator — interactively builds a full <choose>…<when>…</choose> block.
Switch/Case Logic — quick reference for <switch>/<case> structure.
Switch Case Creator — interactively builds a full <switch>…<case>…</switch> block.
Other setEventAttribute Functions — catalog of built-in functions (e.g. toDateTime, toInt) usable inside <setEventAttribute>.
Attribute Search — looks up official FortiSIEM event attributes by name/type before wiring them into setEventAttribute.

Advanced

Win Event Schema to Parser — converts a Windows Event schema/sample into starter parsing instructions.
Webhook JSON — scaffolds parsing instructions for webhook-style JSON payloads.
API Poller JSON — scaffolds parsing instructions for API Poller JSON responses.
Regex Special Characters — reference sheet of regex metacharacters that need escaping.
Reserved Characters — reference sheet of characters reserved by FortiSIEM/XML that need escaping.

6. Validations

Click Validate (or just keep typing — checks re-run live) to see how the Parser XML holds up against the Raw Log Samples and its own internal consistency:

  • okRaw log matching — confirms the eventFormatRecognizer and each instruction actually match the raw log samples, flagging samples that don't match anything.
  • warnAttributes — every <_name:pattern> capture is checked against the known FortiSIEM attribute library; unrecognized attribute names are flagged.
  • warnTemporary Variables — capture symbols starting with _ (e.g. $_body) are tracked as temporary variables; using one before it's been set anywhere upstream is flagged.
  • errorPatterns in Scope — every <:patternName> reference is checked against pattern definitions actually visible at that point in the document (respecting <choose>/<switch> nesting), and malformed XML is flagged immediately.

Live results appear as the Attributes, Temporary Variables, and Patterns In Scope panels next to the editor, plus a diagnostics list under the status pill — click the pill to expand or collapse it.

Diagnostics are scoped to your cursor position by default; place the cursor outside any single instruction to see the full cumulative picture.
